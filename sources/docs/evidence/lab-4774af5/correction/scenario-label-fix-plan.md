## Recommended minimal patch after root authorizes source changes

### A. Complete brief copy and strengthen its existing test

Add the six entries to the existing brief dictionary, keeping current legacy wording intact. Suggested pairs, each below the current 150-character limit:

| Scenario | Purpose | What to watch |
| --- | --- | --- |
| DUPLICATE_DELIVERY | Redeliver the original command. The edge inbox and PLC retain its identity and result. | Delivery count increases; the authorized pick must still have only one physical effect. |
| BROKER_TRANSIENT | The first bounded publication attempt is deliberately stopped before broker delivery. | Retry outbox publication with the same command; robot execution remains separately gated. |
| EDGE_TRANSIENT | The first edge-delivery attempt is deliberately stopped before inbox confirmation. | Retry the delivery stage; publisher confirmation alone does not prove consumer acceptance. |
| OPC_UA_DISCONNECT | The first controller-session attempt is interrupted before command acceptance. | Retry the connection stage, then continue through preconditions and physical authorization. |
| PLC_RESTART | Restart the virtual controller after execution, then query the original command. | A changed boot must retain the original result and must not authorize another pick. |
| WMS_UNAVAILABLE | The first WMS acknowledgement fails after the robot outcome has been verified. | Retry business reconciliation only; the robot effect and original command remain unchanged. |

Make the existing all-choices test explicitly reject the unsupported fallback and assert characteristic expected copy for all six new values. Keep an unknown-value test proving unsupported inputs still receive the fallback. An alternative is moving all brief pairs into the canonical catalog, but that is a larger refactor than needed for this defect.

### B. Supply recorded scenario identity in the playback read model

Prefer one optional structured JobPlayback field, for example `execution_scenario: {source: 'GUIDED_SESSION', session_id, fault}`. An absent field means no authoritative guided metadata; `fault: null` inside a present structure means the persisted baseline selection. Do not conflate those states.

Populate it in `apps/api/playback.py` using a read-only lookup: the already-persisted `meta` key `guided:<job_id>` identifies the session, then `execution_sessions.body` supplies `ExecutionSession.fault`. The association is created for every order line at engine.py:353-361, so it remains correct for earlier lines when the session's current job/command changes. Validate the record/association and retain an explicit unavailable state if it cannot be read. Use `Store.readonly_connect` (including PostgreSQL support); **do not instantiate IntegrationStore in a GET helper**, because its constructor creates schema. Do not rewrite existing persisted events or create a new fault merely for display. DeliveryPlayback already calls playback separately for every job, so this read-model field naturally covers full-delivery and saved-history views.

Render a recorded-scenario label from this per-clip metadata, using the supported label catalog. Resolve the label at render time because workflow-guide.js loads after playback.js but before app.js instantiates MotionPlayer. Update the node harness if it now loads the shared catalog. For legacy event-only records, preserve actual recorded fault labels, separate later observation-review injection from the original execution selection, and use neutral text such as 'No execution scenario recorded' when the original selection is absent. Do not infer Happy path from missing/unknown metadata. A known baseline session may say 'Happy path (no injected scenario)'; that describes configuration, not verified success.

For full delivery, derive labels from every clip: one shared recorded selection can use its label; differing selections must say 'Mixed recorded scenarios' or list the actual labels. Never take a current dropdown or whichever IntegrationConsole.session happens to be open as historical replay evidence. Never let an unrecognized recorded fault fall back to Happy path. This fixes existing records without data migration and avoids an additional scenario-list fetch for every 250ms playback poll.

### C. Bind live presentation to current session AND command

This is justified by the source-level post-consent exposure window; the hidden stage-15 text itself is not a visible defect. Introduce a small live-view invalidation helper: increment a dedicated live generation, cancel its scheduled timer, clear text or show 'Waiting for protocol evidence for command <id>', and reset only presentation state whenever session_id or command_id changes, or clear/load invalidates the view. Clear the previous text before render can unhide the new command's panel.

In pollLive, capture that live generation, session_id and command_id. Apply response, error text and finally/reschedule only if all three still match. Verify response.command_id matches before displaying it. A stale request must not clear a newer request's in-flight flag. This also handles same-session multi-line transitions and delayed errors. Keep all operations read-only; do not modify PLC/runtime behavior or claim fresh telemetry before the response exists.
