## Client principles and observable checks

These are implementation/review mappings, not invented usability scores. The five finish-review corrections are resolved (`finish-review-02.md`). The full final campaign and documentation comparison also pass; neither proves full WCAG conformance.

| Principle | Concrete calibration behavior | Observable verification |
|---|---|---|
| Usability | One next permitted calibration action beside the cell; completed journey context is compact | Happy path and 1280x720 recovery assert a complete visible primary action and useful scene |
| Accessibility | Native labelled controls, keyboard activation, focus restoration, numerical 3D alternatives and reduced-motion replay | Real browser keyboard/axe, enlarged text and narrow screenshots; no real screen-reader claim |
| Learnability | Measure -> estimate -> independent check -> explicit approval; short scope explanations and Swedish presenter narrative | First-use captured state; visible no-approval gates; PRESENTER.md's actual actions |
| Discoverability | Camera, capture and evidence selectors remain visible; two source modes; related function highlighted | Browser inspects real selected images, operands, current code and saved source; pressed source mode has visible styling |
| Consistency | Existing Run & watch / Inspect evidence, system font and shared controls remain | Independent finish review compares established desktop/laptop/narrow surfaces |
| Feedback | Current controller state, calibration authority and recorded job outcome are distinguished | Moved-camera, failed-grip, validation and saved-history captures; trace disconnect remains visible |
| Recovery | No target fallback; failed measurements remain; same-ID request recovery requires an explicit action | Invalid-depth, ambiguity, missing-limit and real stopped-server/restart journeys |
| Efficiency | Selection survives refresh/navigation; saved-estimate reuse retains X/Y but requires unused validation | Revalidation browser journey, per-test session selection and stale-response Node cases |
| Cognitive load | Numerical/source/transport details are disclosures; completed protocol sits with replay evidence | Review captures show action/scene together; code scrolling stays bounded on narrow screens |
| Information architecture | Calibration feeds the existing order, command, verification and reconciliation evidence | Browser follows selected capture -> point -> grasp target -> original command -> fresh observation -> WMS outcome |

The customer explanation maps directly to existing inspectable records: distance versus
installation geometry (`runtime-point`/`candidate`); factory optics (`camera-model-report`);
pose variety (`acquisition-report`); geometric estimation rather than reward training
(`candidate` plus its saved `estimation.fit` source); recognition/grasp limits
(`surface-detection`/`runtime-target`); independent acceptance (`validation`/`reference`);
camera versus tool investigation (`routine-check`/`tool-verification`/`investigation`);
and stable-fixture reuse (`candidate.reused_from` plus new validation/approval).
PRESENTER.md gives Swedish explanations and the exact client actions for these records.
